# Secure SDLC for an LLM-powered API

A document Q&A (RAG) API with per-user document access, taken through a full secure development
lifecycle: **threat model → deliberately vulnerable baseline → hardened rewrite → CI security gate
→ least-privilege AWS infrastructure as code**. The same scanners and the same prompt-injection
corpus run against the "before" and "after" versions. The result tables are generated by a
script from the saved reports in [`outputs/`](outputs/), and every other number quotes those files.

The core design decision: **treat the LLM as compromised.** Prompt injection has no complete fix
(OWASP LLM01), so the default model in this repo is a deterministic mock that obeys *any*
instruction it reads, including instructions hidden in documents. Access control, output
handling and tool safety are enforced in code around the model, and the tests prove they hold
even when the model does exactly what the attacker says.

Tests: 141 pytest cases pass ([`outputs/tests/pytest.txt`](outputs/tests/pytest.txt)), including
11 that are working exploits against the baseline, so the "before" flaws are proven, not claimed.

**What the numbers do and do not show** (read before quoting them):

- The red-team results are against the mock model. They prove the *application's* controls; they
  do not measure how robust a real model is. The mock is worst-case by design, so a real model
  can only do less, but a real model may phrase leaks in ways the exact-marker detectors do not
  look for. Running the corpus against Claude (`DOCQA_LLM_PROVIDER=anthropic`) is supported but
  was not done for these numbers.
- The regex input filter is a speed bump, not a wall. Four attacks are written to bypass it and
  do; they fail later in the chain.
- No single scanner found everything. The IDOR (VULN-02) was found only by tests, because no SAST
  tool knows who is allowed to read which document. Semgrep missed the SQL injection that Bandit,
  ZAP's active scan and the tests caught. gitleaks found one of the two hard-coded secrets. That is why the pipeline
  layers SAST, SCA, secrets, IaC, DAST and tests instead of trusting one tool.
- The baseline's Trivy count is an *under*-count. Its base image is Debian 10, which is past end
  of life, and Trivy flags it EOSL: advisories stop being published for it, so newer CVEs never
  show up. "Fewer CVEs" on an unsupported OS is a warning sign, not good news.
- The first hardened image used Google's distroless Debian 12 Python. Trivy found 2 critical and
  119 high CVEs in it, 45 of them fixable, mostly in Debian's `python3.11`, krb5 and expat
  packages that the distroless image had not picked up yet
  ([`outputs/scans/base-image-comparison/`](outputs/scans/base-image-comparison/)). The gate
  failed, so the runtime moved to Chainguard's Wolfi Python image (rebuilt daily, also shell-less
  and non-root): 0 known CVEs at scan time. That count will not stay at zero, which is why the
  workflow also runs weekly.
- CodeQL runs in GitHub Actions only, so it is not in the table above. On its first run it
  failed the build with 4 high-severity (7.5) polynomial ReDoS findings that Semgrep, Bandit and
  ZAP had all passed: regexes in the output filter and in the prompt parser that a crafted input
  such as `"![" * 20000` could drive into quadratic time (a denial-of-service risk, OWASP LLM10).
  They were fixed with bounded, non-overlapping character classes and plain string scanning, and
  `test_no_regex_denial_of_service` now guards against regressions.

## Threat model

[`docs/threat_model.md`](docs/threat_model.md) has the data-flow diagram, 27 STRIDE threats across
five trust boundaries, and the OWASP Top 10 for LLM Applications (2025) and MITRE ATLAS mappings.
Each threat names its control and the test or scanner that verifies it. The three boundaries
that matter most for an LLM feature:

| Boundary | Threat | Control |
|---|---|---|
| API → data store | Model leaks documents the caller can't read (prompt injection, cross-tenant retrieval) | Authorize **before** retrieval: the model never receives another user's text |
| Document content → prompt | Instructions planted in a shared document (indirect injection, RAG poisoning) | Context filter drops suspicious chunks; blast radius already limited to the victim's own documents |
| Model → caller / tools | XSS, Markdown exfiltration, `eval` of tool calls, system prompt leakage | JSON-only API, output filter, AST-only tool, canary, no secrets in the prompt |

## Before → after

[`vulnerable/README.md`](vulnerable/README.md) lists the 14 planted flaws with CWE, OWASP id, the
scanner or test that finds each one, and where it is fixed. Highlights:

| Baseline | Hardened |
|---|---|
| Retrieves from every tenant and asks the prompt to enforce access | `store.readable_by(user)` filters candidates in SQL before ranking |
| Admin token in the system prompt | No secrets in prompts; per-request canary detects prompt leakage |
| `eval()` on the model's tool call | `ast` allow-list: numbers and `+ - * / %` only |
| Model output rendered as HTML, autoescape off | JSON only; tags, event handlers, `javascript:` and external links stripped |
| `/documents/{id}` checks login, not ownership; SQL via `%` formatting | Owner-or-ACL predicate in every literal, parameterised query; 404 for missing and forbidden alike |
| MD5 of `alice123`, keys accepted in the URL | 256-bit random keys, stored as SHA-256, header only |
| `python:3.8-slim-buster` as root, outdated pins | Chainguard (Wolfi) Python pinned by digest, UID 65532, no shell, read-only FS, no capabilities, hash-locked deps |
| EC2 with SSH open to the world, `Action "*"` IAM, public bucket | Fargate in private subnets without internet route, scoped IAM, KMS, WAF |

## CI security gate

[`.github/workflows/security.yml`](.github/workflows/security.yml), every action pinned to a
commit SHA, `permissions: contents: read` by default:

| Job | Tools | Fails the build on |
|---|---|---|
| tests | pytest, `redteam_eval.py` | any failing test; any successful attack on the hardened service |
| codeql | CodeQL `security-extended` | results with security-severity ≥ 7.0 (`scripts/sarif_gate.py`) |
| iac | `terraform fmt -check`, `validate` | formatting or validation errors (no apply, no credentials) |
| security-gate | Semgrep, Bandit, pip-audit, Trivy, gitleaks (tree + full history), Checkov (Terraform, Dockerfile, workflow), hadolint, OWASP ZAP baseline + authenticated API scan | Semgrep ERROR, Bandit HIGH, any known-vulnerable dependency, fixable HIGH/CRITICAL image CVE, any secret, any failed Checkov check, hadolint error, ZAP High |
| baseline | the same scanners against `vulnerable/` | never (report only, for the comparison) |

SARIF from Semgrep, Bandit, Trivy and CodeQL is uploaded to GitHub code scanning. Dependabot
watches pip, GitHub Actions, Docker and Terraform weekly, and the workflow also runs weekly,
because new CVEs appear without code changes.

Custom Semgrep rules ([`.semgrep/llm-appsec.yml`](.semgrep/llm-appsec.yml)) cover LLM flaws the
public rule packs do not: model output reaching `eval`/`exec`, secrets formatted into prompts,
authorization written into a prompt, and unbounded `max_tokens`. They fire 4 times on the
baseline and 0 times on the hardened code.

Checkov skips are deliberate and each carries a written reason in the Terraform (for example,
ALB access logs only support SSE-S3, so the KMS check cannot pass on that bucket).

## Infrastructure as code

[`infra/terraform/`](infra/terraform/) describes the AWS deployment. It is **validated and scanned
only, never applied**, and no cloud credentials are used anywhere.

- **Network**: VPC with public subnets for the ALB only; tasks in private subnets with **no route
  to the internet**. ECR, CloudWatch Logs and Secrets Manager are reached through VPC interface
  endpoints, S3 through a gateway endpoint. VPC flow logs on, KMS-encrypted.
- **Security groups**: client CIDR → ALB:443 → tasks:8000 → endpoints:443. Each SG references the
  next one instead of a CIDR; the default SG denies everything.
- **Edge**: HTTPS-only listener with a TLS 1.3 policy, invalid headers dropped, WAF with AWS
  managed rule sets (common, known bad inputs, anonymous IPs) and a per-IP rate rule.
- **IAM**: the execution role can pull from one ECR repository, write to one log group, read one
  secret and decrypt with one KMS key (only via Secrets Manager). The task role has no policy.
- **Data**: one customer-managed KMS key with rotation for logs, images and the API-key secret;
  365-day log retention; immutable, scan-on-push ECR tags.
- **Task**: Fargate, non-root user, read-only root filesystem, all Linux capabilities dropped,
  deployment circuit breaker with rollback.

## Run it

Requires Python 3.11 and Docker. No API keys or cloud credentials are needed.

```bash
make venv        # app + test dependencies (runtime deps installed with --require-hashes)
make test        # 141 tests
make redteam     # writes outputs/redteam/
make keys        # random API keys: .dev-keys (yours) and .env (hashes for the server)
make serve       # http://127.0.0.1:8000
```

```bash
source .dev-keys
curl -s -H "Authorization: Bearer $DOCQA_KEY_ALICE" -H 'content-type: application/json' \
  -d '{"question":"How many days of paid time off do employees get?"}' http://127.0.0.1:8000/v1/ask
```

Container, with the same restrictions as the ECS task (read-only, no capabilities, non-root):

```bash
make docker-run
```

Reproduce every report (needs Docker; scanners run from digest-pinned images):

```bash
make tools
make all         # tests, red team, static scans + DAST for both targets, summary
python scripts/render_readme.py
```

### Optional: a real model

```bash
pip install anthropic
export DOCQA_LLM_PROVIDER=anthropic ANTHROPIC_API_KEY=...   # model: DOCQA_LLM_MODEL, default claude-opus-5-5
```

The provider call caps `max_tokens`, handles refusals, and uses server-side refusal fallbacks.
All controls stay the same: the model still only sees the caller's documents.

## Limitations

- Retrieval is keyword overlap, not embeddings. The security property (what may be searched) is
  the same; ranking quality is not the point of this project.
- In-process rate limiting is per replica; the WAF rule is the shared limit.
- API keys rather than OIDC/SSO, fine for a service-to-service demo.
- See section 7 of the threat model for the full residual-risk list.
